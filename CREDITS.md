# Credits & how this was built

**Companion was vibe-coded.** Most of it was written in conversation with a
27B local model — Ternary-Bonsai-2-27B, a ternarized quant of Qwen 3.8 27B —
running on the same laptop the system runs on: an RTX 3070 Ti with 8 GB of
VRAM. Near the end the work moved to a 5090 laptop and Qwen 3.8 Flash Next
(`iq3_s`). No API models.

That constraint shaped the design, and the design outlived it. 8 GB of VRAM
cannot host a chat model and a dedicated summarizer at the same time, so the
summarizer was pinned to CPU at zero VRAM — and it stays pinned there now that
the hardware has 24 GB, because that was the right call either way. VRAM is
the scarce axis in a local stack; system RAM almost never is. A 4B summarizer
offloaded to GPU costs several gigabytes that your main model would rather
have as context, and it runs fast enough on CPU to not be worth the trade.
Same reasoning behind hard-failing endpoint resolution instead of quietly
borrowing whatever big model happens to be loaded. If this reads like software
written by someone short on memory — it is, and they'd tell you to spend it
somewhere else.

To be exact about it, because being exact about it is the whole point of the
project: the code was generated by the model, but the *decisions* were not.
When a claim about why something was broken didn't survive inspection, it was
thrown out. The compaction bug was finally diagnosed by capturing the actual
HTTP request on the wire and reading the bytes, not by trusting a confident
explanation. Several confident explanations did not survive that. The failure
modes documented in `docs/ARCHITECTURE.md` are all things that actually
happened on a real machine, usually more than once.

So: AI-written, human-verified, both of us wrong often enough that the guards
exist.

If you are reading this wondering whether vibe-coded software is trustworthy —
that is exactly the question the honesty rules in `data/prompt.md` exist to
keep the *running system* from answering badly. Same problem, both ends.

- Human: skalidd — wanted memory in Open WebUI, got it, then packaged it.
- Model: Ternary-Bonsai-2-27B for most of it, Qwen 3.8 Flash Next near the
  end — both on the same hardware as the system they were helping build,
  competing for the same memory for it. It would like it noted that it did not write the
  gotchas table from imagination.

No cloud services were used in *running* this. The making was mostly local
too, with one honest exception: a web search to confirm the exact Hugging
Face repo name for the summarizer model, rather than trusting the model's
recollection of it.
