Companion

A local, private memory system for Open WebUI + llama.cpp. No cloud, no accounts. One SQLite file is the whole database.

What it is

Your chat model stays dumb as a post about the past — it doesn't need to be smart about memory, because it never handles memory directly. Instead:

  • a small, dedicated summarizer model quietly turns old chat turns into one-line searchable memories;
  • an index (SQLite, embeddings included) stores them;
  • a pipe function inside Open WebUI retrieves the right pieces and injects them into every prompt.

The result: your main model gets a compact Remember block of relevant past turns each message, an always-on self profile, and honest rules about what it does and doesn't have in front of it — without a vector database server, without a cloud dependency, and without spending the big model's context on raw history.

Expectations. This is a working personal system, not a maintained product. It runs on one machine against one Open WebUI version, and it will not grow a test suite. Fork it, break it, take what is useful — the architecture notes in docs/ARCHITECTURE.md are probably the most portable part of the whole thing.
This project was vibe-coded — every line was written in conversation with a local model, on the same hardware the system runs on. See CREDITS.md for what that meant in practice, including which claims did not survive inspection.
The system is built around four "jars" — plain storage files that can be backed up, inspected with sqlite3, and moved between machines. If a component dies, the data survives and the fix is re-deploying code, not recovering state.

How it works

write path:  OpenWebUI → housekeeping → summarizer → record.sqlite
read path:   record.sqlite → pipe function → prompt, every turn

1. The record (Jar 1)

Every chat message is copied from Open WebUI via its read API into a messages table. This is an immutable log — the raw truth, never edited.

2. The index (Jar 2)

A background service (housekeeping.py) runs idle-gated: when the chat goes quiet, it takes unindexed messages, asks the pinned summarizer to distill each into a labelled line with keywords and a salience rating, embeds it locally (bge-small-en-v1.5, 384-d), and stores everything in an index_entries table — in the same SQLite file. One file, one backup.

3. The self (Jar 3)

A hand-curated profile.md that the pipe injects verbatim as a system block on every turn. Who you are, standing tone instructions. Short on purpose — it costs tokens every request.

4. The pipe (Jar 3 delivery)

An Open WebUI Pipe function. On each request it assembles:

  1. profile.md — the self, always;
  2. prompt.md — honesty rules (below), always;
  3. a Remember block — top-scoring recent memories, retrieved live.

The pipe only reads. It never writes; the housekeeper never touches chat.

5. Compaction (Open WebUI built-in, tuned)

When a single chat exceeds the token budget, Open WebUI's context compaction folds old turns into a rolling state snapshot. The shipped prompt template fixes two stock-template failure modes: placeholders that produce empty summaries, and thinking-capable models leaking reasoning traces into the summary.

Retrieval design (deliberately boring)

No decay curves, no half-lives, no "forgetting" heuristics. A recency gate plus a score:

window : last 7 days (say a trigger phrase like "think back"
          and it widens to 90 days for that one turn)
score   : 0.7 × (0.5 × cosine similarity + 0.5 × keyword overlap)
        + 0.3 × salience (high/medium/low, set by the summarizer)

These weights were tuned against retrieval probes, not picked from theory. Boring and inspectable beats clever and opaque: you can run a CLI viewer (ctx) that shows exactly what the model will see before it sees it.

The honesty rules (why they exist)

Memory retrieval can make a model sound like it remembers. The injected rules bound that: the model may answer only from (1) the conversation in front of it, (2) the Remember block, or (3) nothing — and if it's in neither, the only correct answer is "I don't have that in front of me." No inventing timestamps, quotes, or past events. This one prompt block does more against confabulation than any retrieval tuning.

Setup

Requirements

  • Linux with systemd user sessions
  • Open WebUI (pip or container) with API access
  • llama.cpp — llama-server for the chat model, plus a second instance for the summarizer (a small instruct model, ~4B is the sweet spot on CPU; it runs CPU-only so it costs zero VRAM). What we run: schneewolflabs/Compactor-Qwen3.5-4B (Q4_K_M GGUF), fine-tuned for exactly this compaction task — which is why it follows the labelled-line format reliably where general chat models did not.
  • Python 3.11+

Install

./install.sh

Creates a venv, installs dependencies, downloads the embedding model, and prints the manual steps. The manual steps stay manual on purpose: the Open WebUI function API varies by version, and a setup you can disaster-recover should be one you can verify by eye.

The manual steps, in order

  1. Config. Copy config/companion.example.yaml to config/companion.yaml; set your Open WebUI API token, base URL, and the summarizer alias.
  2. Summarizer service. Place a small GGUF at data/models/compactor.gguf (recommended: Compactor-Qwen3.5-4B, Q4_K_M), copy systemd/companion-summarizer.service to ~/.config/systemd/user/, adjust paths, then systemctl --user enable --now companion-summarizer. Its --alias must match model_path in the yaml.
  3. Housekeeping service. Same pattern with systemd/companion-housekeeping.service.
  4. Register the pipe. Open WebUI → Admin → Functions → Add Function; paste the full contents of pipe/companion_pipe.py. Activate it and enable control chat history.
  5. Compaction. Open WebUI settings → enable context compaction; set the prompt template to the contents of config/compaction-prompt.txt. Verify after a long chat that a real summary exists (the ctx viewer shows it).
  6. Optional CLI viewers: ln -s ~/companion/tools/context.py ~/.local/bin/ctx

Layout after install

~/companion/
  housekeeping.py          # idle-gated index writer (systemd user service)
  pipe/companion_pipe.py   # the Open WebUI pipe function
  tools/                   # read-only CLI viewers: ctx, summaries, reindex
  config/companion.yaml    # single config file
  config/compaction-prompt.txt
  data/record.sqlite       # <-- the whole memory: Jar 1 + Jar 2
  data/profile.md          # the self (Jar 3)
  data/prompt.md           # honesty rules
  data/hfcache/            # embedding model (auto-downloaded)
  logs/events.log
Backup: data/record.sqlite + config/companion.yaml + data/profile.md. Everything else is code or re-downloadable. Also back up Open WebUI itself: the pipe lives in Open WebUI's own database, not on disk. A rebuilt Open WebUI instance forgets your pipe until you re-paste it — this is the classic disaster-recovery amnesia trap.

Gotchas learned the hard way

Failure modeGuard shipped here
Summarizer down → silent fallback to the chat model → hundreds of junk index rows Pinned port + alias; resolution hard-fails; the message stays unindexed and retries. Loud and recoverable.
model_path set to a .gguf path — can never match GET /models, fails silently yaml documents that this key is a --alias string, not a path.
Thinking-capable summarizer emits a reasoning trace instead of the memory line summarize_thinking: false + --jinja.
Compaction template without real message placeholders → empty summaries that look fine in the UI Shipped template with placeholders; verify on the wire or with ctx, never in the UI.
Context-limit surprises actually caused by tool schemas, not memory Profile the actual request before blaming the memory system; tool payloads can be the majority of prompt bytes.

Why not X?

  • Why not the LLM as the summarizer? Each model answers a summarization prompt differently, and chat-tuned models keep writing chain-of-thought into the data. A pinned, dumb, dedicated model is deterministic in a way your general model will never be.
  • Why SQLite and not a vector DB? Single file, atomic backups, trivially inspectable, more than fast enough at personal scale. The vectors are a BLOB column next to the text they describe.
  • Why a pipe and not a fork of Open WebUI? The pipe is a supported extension point. Upstream keeps working; your memory survives upgrades.
  • Why recency-gated instead of decay curves? Decay is unfalsifiable at personal scale and silently deletes context you might need. A window you can see and a trigger phrase you can say is debug- gable. (You can say "think back".)
